# Security policy

## Reporting a vulnerability in these charms

Please report security issues in the charms to **security@ubuntu.com**.

Include as much of the following as you can:

- which charm is affected (`odk-central-k8s`, `enketo-k8s`, `pyxform-k8s`);
- the charm revision and channel, and the ODK Central release it deploys;
- Juju version and Kubernetes flavour;
- what an attacker can achieve, and the steps to reproduce it.

You will get an acknowledgement within **5 business days**. We follow
coordinated disclosure: please give us a reasonable window to ship a fix before
publishing details.

Canonical's full disclosure policy is at
<https://ubuntu.com/security/disclosure-policy>.

## Reporting a vulnerability in ODK Central itself

If the issue is in the upstream workload rather than in the charm code — the
Central API, the frontend, Enketo or pyxform — report it to the ODK project at
<https://github.com/getodk/central/security>. Please let us know as well, so we
can track the fix and pin a patched release.

## Scope notes

- Every credential these charms handle is a Juju secret. If you find a way to
  read one out of `juju config`, charm logs, action output beyond the single
  intended return, or a rendered config file readable by an unexpected
  container, that is in scope.
- The three shared Enketo secrets are generated by `odk-central-k8s` and granted
  to `enketo-k8s` over a relation. Anything that lets a third application obtain
  them is in scope.
- These charms deliberately terminate TLS at `traefik-k8s` and run the workload
  nginx on plain HTTP behind it. Reports that "the workload serves HTTP" are not
  vulnerabilities on their own; a way to reach the workload port bypassing
  ingress is.
