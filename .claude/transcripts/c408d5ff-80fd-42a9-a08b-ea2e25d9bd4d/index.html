Architecture Decisions (pre-resolved)

These decisions are final. Do not re-debate them during the build.

Kubernetes-only for v1. postgresql-k8s, traefik-k8s, s3-integrator, smtp-integrator and the COS charms all have mature k8s variants, and upstream ships only container images. A machine charm is out of scope for this build.

Three Juju applications, seven containers. The group is:

Charm Containers Why separate
odk-central-k8s service, nginx The API and the frontend/reverse-proxy are released together and version-locked; they belong in one application
enketo-k8s enketo, plus redis-main and redis-cache under Q5 default Enketo is an independently versioned upstream (enketo/enketo) with its own state; it scales and upgrades on its own cadence
pyxform-k8s pyxform A stateless XLSForm→XForm converter with its own release train; separating it makes the conversion service replaceable and independently scalable

Do not collapse these into one application. The cross-charm bootstrap ordering and the provided interface are the point of the exercise.

SSL_TYPE=upstream. Upstream's nginx image can obtain Let's Encrypt certificates itself. In Juju, TLS is traefik-k8s's job. Set SSL_TYPE=upstream so nginx serves plain HTTP on 80 and trusts X-Forwarded-Proto. Never enable certbot inside the charm.

No secrets container. Upstream's one-shot secrets container writes three files to a shared Docker volume. Juju has no shared volume between applications, so odk-central-k8s generates all three values in its install hook, stores them as application-owned Juju secrets, and distributes them to enketo-k8s over the odk-enketo relation. This is the charm-group design's centrepiece.

Exact secret lengths are load-bearing. files/enketo/start-enketo.sh upstream asserts, with stat -c "%s", that /etc/secrets/enketo-secret is exactly 64 bytes, /etc/secrets/enketo-less-secret exactly 32 bytes, and /etc/secrets/enketo-api-key exactly 128 bytes. Enketo refuses to start otherwise. When the enketo-k8s charm pushes these files with Pebble, write no trailing newline and assert the length in charm code before pushing. A stray \n is a 65-byte file and a hard startup failure with an unhelpful message.

Two new charm libraries, written here. No published charmlib exists for either interface. Write and ship:

  • lib/charms/odk_central_k8s/v0/odk_enketo.py — OdkEnketoProvider (in odk-central-k8s) and OdkEnketoRequirer (in enketo-k8s). Provider sends: secret IDs for the three shared secrets, and the public base URL. Requirer sends back: the in-cluster Enketo URL that Central puts in config.json under enketo.url.
  • lib/charms/pyxform_k8s/v0/xlsform.py — XlsformProvider (in pyxform-k8s) and XlsformRequirer (in odk-central-k8s). Provider sends host and port; requirer consumes them into config.json under xlsform.

Both are bidirectional; model them on data_platform_libs conventions for event naming (*_ready, *_gone) and emit custom events rather than making the charm handle raw relation-changed.

Charm libraries over hand-rolled requirers everywhere else. Where a published charmlib exists for a relation interface, import it. Hand rolling is acceptable only for the two ODK-specific interfaces above.

Redis default is in-charm (Q5). redis-main and redis-cache run as sidecar containers in enketo-k8s, redis-main mounting a Juju filesystem storage at /data with upstream's persistence settings (save 300 1, appendonly no, dbfilename enketo-main.rdb) and redis-cache running with persistence off. The charm ALSO declares optional redis-main and redis-cache relations (interface redis); when either is related, the corresponding sidecar is stopped and the relation endpoint is used instead. Attempt the relation path once in Phase 6 against redis-k8s --channel latest/edge and record the result in docs/day2-ops.md whichever way it goes.

Pebble service startup order

odk-central-k8s:

  1. Block until postgresql relation data is complete.
  2. Render /usr/odk/config/local.json (or wherever the image expects its config — verify against the image, see Phase 4) from the template, including database, email, xlsform, enketo, oidc and s3blobStore stanzas.
  3. Run migrations as a one-shot Pebble service (migrations, startup: disabled, started by charm code, exit code checked).
  4. Start service; gate ActiveStatus on GET http://localhost:8383/v1/version.json returning 200.
  5. Start nginx only once service is healthy — the nginx config proxies to it and will fail its own healthcheck otherwise.

nginx additionally needs DOMAIN, SSL_TYPE=upstream, HTTPS_PORT and OIDC_ENABLED in its environment because it templates client-config.json for the browser at container start. Changing any of those is a re-render and reload, not just a restart: the file is read by the frontend at page load.

enketo-k8s:

  1. Start redis-main and redis-cache (or verify the relations).
  2. Block until the odk-enketo relation supplies all three secrets and the base URL.
  3. Push /etc/secrets/enketo-secret (64 B), enketo-less-secret (32 B), enketo-api-key (128 B) with exact lengths, no newline.
  4. Render config.json from the template with SECRET, LESS_SECRET, API_KEY, BASE_URL, DOMAIN and the two Redis endpoints.
  5. Start enketo; gate ActiveStatus on port 8005 accepting connections.

pyxform-k8s: single service, starts immediately, no dependencies. It is the only charm in the group that can reach ActiveStatus standalone.

Cross-charm bootstrap ordering

pyxform-k8s ──(xlsform)──▶ odk-central-k8s ──(odk-enketo)──▶ enketo-k8s
                                  ▲                                │
                                  └──── enketo URL sent back ──────┘

odk-central-k8s cannot render a complete config.json until BOTH the xlsform relation (host/port) and the odk-enketo relation (Enketo's URL, which Enketo only sends after it has received the secrets Central generated) are settled. That is a genuine two-way bootstrap: Central must publish secrets before Enketo can start, and Enketo must publish its URL before Central's config is complete.

Implement it as: Central writes secrets and base URL immediately on relation-created; Central starts with enketo.url pointing at a placeholder and sets WaitingStatus("waiting for enketo"); on receiving Enketo's URL it re-renders and restarts service. Do not block Central's startup on Enketo — that deadlocks the group.

External ports (charm-internal; traefik maps these)

  • service: 8383 (HTTP, API)
  • nginx: 80 (HTTP, serves frontend + proxies /v1 to service and /- to Enketo)
  • enketo: 8005 (HTTP)
  • pyxform: 80 (HTTP)
  • redis-main: 6379, redis-cache: 6380 (note the non-default port on the cache instance — upstream's config sets it and Enketo's config expects it)

Storage requirements

  • odk-central-k8s: none. All state is in PostgreSQL and, once the S3 relation exists, the blob store.
  • enketo-k8s: redis-main-data, type: filesystem, minimum-size: 1G, mounted at /data in the redis-main container. redis-cache is deliberately ephemeral.
  • pyxform-k8s: none.

Losing redis-main loses in-flight form and instance state in Enketo. Say so in docs/day2-ops.md — it is the one piece of state in the group that is not in PostgreSQL or S3.
